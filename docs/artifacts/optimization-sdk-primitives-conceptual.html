Part one

What is true of every SDK in the suite

The suite ships packages for React Web, Next.js, plain browser, Node, and React Native. They differ in how they hold state, not in what they do.

01

The decision object

You ask the Experience API who this visitor is. It answers with one small object — OptimizationData — carrying three things: a profile (who we think this visitor is, plus traits), selectedOptimizations (which experience won, and which variant index), and changes (merge-tag and flag substitutions).

Every SDK in the suite receives this same shape. Stateful runtimes — browser, mobile — put it into reactive state. The stateless Node SDK hands it back to the current request and forgets it.

The habit to build immediately. An event can be accepted without carrying data yet, so both the acceptance flag and the data need checking before you read. Blocked events don’t throw — they come back unaccepted, quietly.
02

The baseline join

You fetch an ordinary Contentful entry — the baseline. The SDK joins it against the visitor’s selections and hands back either the authored variant or the baseline, untouched. That join is the whole product surface; everything else exists to decide where it happens and who owns the visitor’s identity while it does.

Two things that bite on day one. A control assignment carries variantIndex: 0 — it returns the baseline entry, but the selection metadata is still there. So comparing the resolved entry against the baseline by identity does not tell you whether an experience matched. And your component must render identically from baseline or variant: same content type, all content arriving through props. A component that fetches its own data cannot be personalized.
03

One root, and a fixed lifecycle order

Create exactly one runtime root or process singleton per app. Then the order matters, because selections do not exist until the initial page event comes back.

The split worth internalizing: browser and mobile runtimes hold state across a session. The Node SDK is request-scoped — you create a per-request client with forRequest(), and its events live on that object, never on the singleton. Node stores nothing between requests, so carrying the profile forward is your job.

04

Consent is two independent axes

Not one switch, two: may we send events, and may we retain a profile across visits. A single boolean sets both; the object form lets them differ — analytics with no durable identity, for instance. With no decision recorded at all, the state is undefined, not false.

Your application owns

The consent record itself, the banner or CMP, and the policy. The SDK renders no consent UI and never decides for you.

The SDK owns

One cookie — ctfl-opt-aid — carrying profile identity so the server and the browser agree on who this visitor is.

Do not mark ctfl-opt-aid HttpOnly. The browser SDK reads it from document.cookie at startup to continue the profile the server established. Lock it away and server-to-browser identity continuity breaks silently, with no error anywhere.

Resolution never reads consent. No consent simply means no selections arrive, and no selections resolve to baseline — which is why a consent bug and a content bug look identical from the page.

05

The Contentful fetch contract

The single largest cause of “it renders the baseline and I can’t see why.” Personalization lives at the end of a chain of links, and the resolver can only match links that came back fully resolved.

Three payload rules, and how each one fails
RuleWhySymptom when broken
One concrete locale All-locale payloads produce locale-keyed field maps the resolver cannot read. Never withAllLocales or locale=*. Always baseline.
Enough include depth Unresolved links can’t be inspected, so they are filtered out before matching. Always baseline.
Publish in dependency order Variants, then experiences, then baseline. The Delivery API only sees published content. Works in preview, fails in production.
06

Where you resolve decides flash versus cacheability

Not an SDK setting — the one architecture decision the SDK forces, and the same decision in every framework. The flash is simply the gap between the first byte arriving and the Experience API answering.

Resolve in the browser

Page stays static and CDN-cacheable.

Flashes baseline before the variant appears.

Worst above the fold, where the flash is most visible — and personalization usually is.

Resolve on the server

No flash — correct content in the first byte.

Route renders per request, not shareable.

Only the personalized routes pay this. Everything else keeps whatever cache policy you like.

Part two

Next.js App Router specifics

The Next.js adapter is a thin binding, not a new runtime — it wires the Node SDK for request-time decisions to the React Web SDK for after hydration. Seven things are particular to it.

01

Import subpaths, never the package root

The root of @contentful/optimization-nextjs has no runtime export at all. That is deliberate: each subpath is one runtime and one type surface, so the server/client boundary stays visible in your import lines. For a basic build you need four — /app-router/server for the binding, /request-handler for the proxy, /client for browser hooks, and /app-router/client if you bind inside Client Components.

Older material will send you wrong here. A fair amount of writing describes a factory called createNextjsAppRouterOptimization imported from a bare /app-router path. In 1.2.0 neither exists — the factory is bindNextjsAppRouterServerOptimization, and the only App Router subpaths are /app-router/server and /app-router/client. When a name won’t resolve, read the installed package’s own README rather than the guide you were following.
02

Bind once, in a server-only module

One call to bindNextjsAppRouterServerOptimization, in one module, imported everywhere else. A second binding creates a second SDK instance competing with the first for the same visitor. Importing server-only at the top turns an accidental client import into a build error rather than a leak.

The configuration is small: a client ID and environment, one concrete locale, a consent block with a server resolver plus client defaults, and — only if you want the SDK to do the fetching — a contentful client.

03

The proxy boundary is required, not optional

Server Components cannot see the incoming request URL on their own. createNextjsOptimizationContextHandler forwards sanitized URL, headers, and cookies so the request-personalized runtime can resolve a variant before markup is sent.

The filename and export name changed with Next.js 16: proxy.ts exporting proxy, where 13–15 used middleware.ts exporting middleware. The body is identical, and the matcher must cover every route that personalizes per request.

This one fails loudly, which is a mercy. Wrong filename, wrong export name, or a matcher that misses the route, and the bound root throws. It does not quietly fall back to baseline — so an error mentioning the handler at startup points straight here.
04

Two surfaces: the request family versus the top-level members

If you remember one Next.js-specific thing, this is it. The binding hands you the same components twice, and the only difference is whether they read the request.

Four members hang off the request family: OptimizationRoot, OptimizationProvider, OptimizedEntry, and NextAppAutoPageTracker. The cacheable side is where createPublicPermutationHandoff and OptimizationAnalyticsRoot live. Naming the two sets apart on import — Request* and Explicit* — costs a few keystrokes and prevents the mistake this separation exists to catch.

05

The handoff

The server picked a variant. Now the browser has to hydrate without undoing that decision. The handoff is the object carrying it across the boundary.

The request family builds its handoff automatically and marks it private-request. You only construct one by hand — via createPublicPermutationHandoff — when you are deliberately building something shareable.

06

Root, tracker, entry — the three things you render

OptimizationRoot wraps the participating tree: the provider plus initial page-event wiring. NextAppAutoPageTracker emits the page view. OptimizedEntry is a render prop that hands your component the resolved entry. That is the whole rendering surface.

Three constraints, each of which will catch you once. The tracker reads search params, so it must sit inside a Suspense boundary. Exactly one owner emits the initial page event — server or browser, never both, or every visit double-counts. And OptimizedEntry takes exactly one source: a baseline entry your app fetched, or an entry ID / managed-entry descriptor for the SDK to fetch. Passing two is an error, not a preference.
07

A personalized route is a dynamic route

Primitive 06 from part one, expressed as Next.js configuration. Reading cookies or headers opts a route out of static generation — correct, and what you want. The failure is leaving static-generation directives on that same route, where the two intentions contradict each other: generateStaticParams, a force-static flag, or a revalidate value.

A route that genuinely must stay cached has two honest options: keep personalization client-side there and accept the flash, or serve it from a public-permutation handoff. What it cannot do is run the per-request server preflight for its own markup.
