The app-local aliases — Request* versus Explicit* — are deliberate teaching scaffolding, not house style. They encode which family a route belongs to, and TypeScript enforces the difference.

Start training here

NextjsAppRouterRequestOptimizationRootProps is an Omit of routeKey, handoff, hydration, buildPagePayload, and initialPagePayload.

You physically cannot hand the request root request plumbing. The explicit root requires all of it. This one type prevents the most common mistake — hand-rolling cookies() / headers() / route-key plumbing the request family already owns.

02 · Question one

Caching, SSR vs CSR, and the boundary files.

Integration with default Next.js features

Cache Components is on, and it changes the composition rules

next.config.ts:8 sets cacheComponents: true. Three consequences are visible in the code.

connection() goes at every private boundary, not once per route. app/(request)/layout.tsx:13 and app/(static)/static-shell-private-slot/PrivateRequestSlot.tsx:11 each call it. Suspense alone does not defer a subtree to request time, and one connection() higher up does not cover a nested boundary. The static-shell route is the demonstration: a fully static shell with one request-time island beneath Suspense.

Revalidation lives on the cached function, never on the route. app/(static)/selection-handoff/[segment]/page.tsx:15-33 puts 'use cache', cacheLife({ revalidate: 60 }), and cacheTag(...) inside loadSelectionHandoffPage(). There is no export const revalidate anywhere — Cache Components ignores it.

generateStaticParams() and the handoff share one registry. getCustomerSegmentStaticParams() drives SSG params, getCustomerSegment() drives the handoff. One source of truth for the permutation set.

The SDK cache key and the Next.js cache key are different things

This is the highest-value caching callout on the page.

handoff.cache.key is SDK transport and identity metadata — rendered to the page at line 49 purely so E2E can assert on it. It is not a use cache key and not a cacheTag(). The tags are app-authored: lib/optimization.ts:125-127 mints ctfl-opt-segment:${slug}:v${cacheVersion}, and the app is what carries them into Next's cache system. Nothing in the SDK does that for you.

One proxy, two SDK helpers, dispatched by pathname

  • Public-permutation paths go to createNextjsPublicPermutationCacheMiddleware() from /cache-middleware, which rewrites to an SDK-owned ctfl-opt-cache-key query param so the CDN and Next cache split per permutation. resolveCache returning undefined for an unknown segment cleanly opts that request out.
  • Everything else goes to createNextjsOptimizationContextHandler() from /request-handler, which forwards sanitized request-context headers so Server Components can see the request.

proxy.ts is Next.js 16 naming. On 13–15 the same body lives in middleware.ts with a middleware export. Note why proxy.ts exists as a two-line file: the handler is re-exported from lib/optimization.ts, but config.matcher must be a literal array in the boundary file for Next's static analysis to see it.

SSR to CSR takeover, and per-route hydration policy

lib/optimization.ts:51-56 is the most elegant thing in the implementation.

Hydration policy is a pure synchronous function of routeKey, declared once in the binding. No route file knows or cares.

Hydration modeFirst-paint ownerBrowser behavior
preserve-server server / static / ISR / edge markup Markup stays continuously visible while the live SDK adopts it.
client-only-hidden-until-ready browser Baseline layout target can stay hidden until selected, baseline, or fallback content commits.
analytics-only server markup Hydrates analytics state only. No content resolution context at all.

And the route follows through: /hidden-until-ready renders LiveEntryCard, a client OptimizedEntry, rather than RequestOptimizedEntry — consistent with the browser owning resolution there.

The server / client split follows one rule

  • Server tree by default. components/EntryCard.tsx has no 'use client' and renders RequestOptimizedEntry directly.
  • Reach for the /client OptimizedEntry only when you need per-entry liveUpdates or loadingFallback — components/LiveEntryCard.tsx:4,16. The home page shows all three states side by side: inherit, true, false.

Quiet footgun

next.config.ts:10-23 maps every PUBLIC_* var into env. lib/config.ts reads process.env at module scope, in a module imported by both server and client code. Without that env map the client binding silently receives an undefined clientId — no error, no warning.

Cleanest bridge example in the repo

serverConsent at lib/optimization.ts:39-40 is a NextjsOptimizationServerConsentResolver. It receives { cookies, headers } and returns either false or { events, persistence }.

It reads the app's own cookie, app-personalization-consent. The SDK never owns your consent UX — it just asks you. Three matching readers exist: the server cookie jar (util.ts:27), the browser cookie (util.ts:12) feeding clientDefaults, and the reactive useConsentState() in lib/hooks.ts:12.

Client binding — lib/optimization-client.ts

bindNextjsAppRouterClientOptimization() at :19 exports only RequestOptimizationRoot, as ClientRequestOptimizationRoot (:44), which lib/optimization.ts:60 injects back into the server binding.

This inversion deserves its own slide. The beforeInitialPage.run callback (:32-40) does browser work — reading window.location.search, calling identify() — before the root's one-time initial-page decision. The callback never crosses the server boundary; only a Client Component reference does. Both server binders declare beforeInitialPage?: never and reject a client config containing it, so the callback stays out of Server Components, request config, Flight data, the handoff, cache state, ISR, and Edge helpers.

Two consequences to teach explicitly:

  • The injected root becomes the sole page-event owner for its subtree, so RequestNextAppAutoPageTracker must not be mounted. This app never imports it — correct.
  • maxWaitMs (here 2_500) is a watchdog, not a cancellation. It defaults to 3000 and synchronously throws TypeError on 0, negatives, NaN, or Infinity. Return every promise from run; fire-and-forget work becomes "later activity" and is not waited on.

04 · Question three

The subtleties that earn their place in a training session.

Other things worth calling out

Entry-fetch ownership is a real architectural choice, shown both ways in one file

components/EntryCard.tsx:22 takes baselineEntry — app-owned, via loadPageEntries in lib/contentful.ts with include: 10 and an explicit locale. :55 ManagedEntryCard takes entryId — SDK-owned, via contentful: { client }.

Only the SDK-managed path overlaps request initialization with the CDA read. The pairing to teach: RequestOptimizationRoot prefetchManagedEntries={[entryId]} at PrivateRequestSlot.tsx:16 warms the baseline and merges it into the browser handoff, so the client does not repeat the fetch. A server OptimizedEntry alone fetches for that render only.

isEmptyVariant is handled for you in one path and not the other

In analytics-only/page.tsx:60,68 the app must check it, because resolveEntriesForSelections() is a raw resolver. The same check appears inside the ExplicitOptimizedEntry render prop at selection-handoff/page.tsx:60 — but server-entry-renderer.tsx:95 returns null before invoking children, so that branch is unreachable.

Harmless, and it reads as intentional documentation. The honest teaching point: bound entry components suppress empty variants; the raw resolver does not.

Analytics-only routes have no entry component at all

The cleanest illustration of the mode. Content is resolved offline inside 'use cache', rendered as plain markup, and the browser runtime learns what to observe purely from attributes spread onto a <section>.

AppShell analyticsOnly swaps out the event log for that route, because there is no content-resolution context to read.

Public permutations require an app-owned registry, and the SDK says so

lib/customer-segments.ts deep-clones fixtures into { slug, cacheVersion, locale, baselineEntryIds, selectedOptimizations }. The concept doc is blunt: public and static handoffs must use app-owned selections, never request profile, cookie, or header data, and the SDK "does not discover public permutations for the application."

Note that the baseline segment uses selectedOptimizations: [] — an explicit "no selection applies," which resolves baseline content with matching baseline tracking metadata. That is meaningfully different from "not configured."

The preview panel is a separate, lazily-loaded package

PreviewPanel.tsx:15-24 dynamically imports @contentful/optimization-web-preview-panel and the CDA client inside an effect, gated on both a feature flag and sdk !== undefined. That keeps the panel out of the main bundle, and it must live inside the provider subtree because it reads useOptimizationContext(). Both mounting sites place it immediately inside the request root.

Locale discipline

appConfig.locale is the single source for SDK config, event context, and every CDA call (lib/contentful.ts:63). Entries stay single-locale — no withAllLocales, no locale=*. This is a hard repo rule because variant resolution cannot reliably resolve multi-locale entry shapes.

05 · Gaps

Useful as discussion prompts, not defects.

Three honest gaps

Unexercised surface

createHandoffFromSelections and createOptimizationCacheKey are re-exported at lib/optimization.ts:69-70 but used nowhere in the app. Available surface, unexercised here.

Deliberately off

request.trustedRequestHandoff is not enabled — correctly, because createNextjsOptimizationContextHandler() is called with no options at lib/optimization.ts:97.

Turning it on requires configuring the handler with sdk and consent. The payoff is skipping a second page() call and avoiding duplicate first page events, via the forwarded x-ctfl-opt-server-data. Good "what's the next optimization" question for a trainee.

Not a production pattern

lib/contentful.ts:68-70 swallows CDA errors and returns undefined entries, which every page renders as "unavailable." Deliberate for E2E determinism, and explicitly not something to copy.

06 · Curriculum

This one really is a sequence — each step depends on the last.

Reading order for a trainee

  1. lib/optimization.tsThe whole contract, in 168 lines.
  2. proxy.ts + next.config.tsThe two boundary files. Short, and they explain each other.
  3. app/(request)/layout.tsx → components/EntryCard.tsxThe private path, end to end.
  4. app/(static)/static-shell-private-slot/Cache Components composition. Read both files — the connection() placement is the point.
  5. app/(static)/selection-handoff/[segment]/Public permutation, plus the cacheTag bridge.
  6. app/(static)/analytics-only/[segment]/The no-runtime-resolution contrast.
  7. lib/optimization-client.tsThe injection inversion. Last, once everything else makes sense.

Behavior is pinned by lib/e2e-web/e2e/: handoff, readiness, ssr, live-updates, variant-resolution, tracking, and navigation specs. readiness.spec.ts and handoff.spec.ts exercise beforeInitialPage and the cache-key rewrite respectively, so they are the fastest way to watch the subtle parts assert themselves.
