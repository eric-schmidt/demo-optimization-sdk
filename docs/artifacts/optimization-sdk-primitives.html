Part one

What is true of every SDK in the suite

The suite ships packages for React Web, Next.js, plain browser, Node, and React Native. They differ in how they hold state, not in what they do. These six things are the same everywhere.

01

The decision object

You ask the Experience API who this visitor is, and it answers with one small object called OptimizationData. Every SDK in the suite receives this same shape. Stateful runtimes — browser, mobile — put it into reactive state; the stateless Node SDK hands it back to the current request.

The one habit to build now: an event can be accepted without carrying data yet, so check both before you read.

02

The baseline join

You fetch an ordinary Contentful entry — the baseline. The SDK joins it against selectedOptimizations and hands back either the authored variant entry or the baseline, untouched. That join is the whole product surface.

It is fail-soft by design. If nothing matches, if links are unresolved, if the entry was never personalized — you get the baseline. That is a success, not an error, and it must render normally.

Two things that bite on day one. A control assignment has variantIndex: 0 — it returns the baseline entry but selectedOptimization is still defined, so never infer “nothing matched” from resolved.entry === baselineEntry. And your component has to render identically from baseline or variant: same content type, all content arriving through props. A component that fetches its own data cannot be personalized.
03

One root, and a fixed lifecycle order

Create exactly one runtime root or process singleton per app. Then the order is not optional: initialize, seed consent and identity, emit the initial page (or screen) event, and only then resolve entries. Resolve before the event lands and you have no selections to resolve against.

The split worth internalizing: browser and mobile runtimes hold state; the Node SDK is request-scoped, and its events live on the object forRequest() returns — not on the singleton.

04

Consent is two independent axes

Not one switch, two: may we send events, and may we retain a profile across visits. A boolean sets both at once; the object form lets them differ — analytics with no durable identity, say.

Your app owns the consent record and every piece of consent UI. The SDK owns exactly one cookie, ctfl-opt-aid, which carries profile identity.

Do not mark ctfl-opt-aid HttpOnly. The browser SDK reads it from document.cookie at startup to continue the profile the server already established. Lock it away and server-to-browser identity continuity breaks — silently, with no error anywhere.

Note that resolution never reads consent. No consent simply means no selections arrive, and no selections resolve to baseline — which is why a consent bug and a content bug look identical from the page.

05

The Contentful fetch contract

This is the single largest cause of “it just renders the baseline and I can’t see why.” Three rules, all about the shape of the payload you hand the resolver.

The three payload rules, and how each one fails
RuleWhySymptom when broken
One concrete locale All-locale payloads produce locale-keyed field maps the resolver cannot read. Always baseline.
Enough include depth The chain is entry → nt_experiences → nt_variants → variant content. Unresolved links get filtered out. Always baseline.
Publish in dependency order Variants, then experiences, then baseline. The Delivery API only sees published content. Works in preview, fails in production.
06

Where you resolve decides flash versus cacheability

This is not an SDK setting — it is the one architecture decision the SDK forces you to make, and it is the same decision in every framework. You cannot have both.

Resolve in the browser

Page stays static and CDN-cacheable.

Flashes baseline before the variant appears.

The server does no per-visitor work, so one cached HTML document serves everyone. Worst above the fold, where the flash is most visible.

Resolve on the server

No flash — correct content in the first byte.

Route renders per request, not shareable.

Reading cookies and headers is what makes it per-visitor, and that is exactly what makes the output un-shareable across visitors.

Only the personalized resolution is per-request. Routes that don’t personalize, and the raw baseline content itself, can still follow whatever cache policy you like.

Part two

Next.js App Router specifics

The Next.js adapter is a thin binding, not a new runtime — it wires the Node SDK for request-time decisions to the React Web SDK for after hydration. Seven things are particular to it.

01

Import subpaths, never the package root

The root of @contentful/optimization-nextjs has no runtime export at all. That is deliberate: each subpath is one runtime and one type surface, so server and client boundaries stay visible in your import lines.

Older material will send you wrong here. A fair amount of writing describes a factory called createNextjsAppRouterOptimization imported from @contentful/optimization-nextjs/app-router. In 1.2.0 neither exists — there is no bare /app-router export, only /app-router/server and /app-router/client. When a name doesn’t resolve, check the installed package’s own README rather than the guide you were reading.
02

Bind once, in a server-only module

One call, one module, imported everywhere else. A second binding creates a second SDK instance competing with the first for the same visitor. The server-only import is what turns an accidental client import into a build error instead of a leak.

03

The proxy boundary is required, not optional

Server Components cannot see the incoming request URL on their own. This handler forwards sanitized URL, headers, and cookies so the request-personalized runtime can resolve a variant before markup is sent. Skip it and nothing works.

The filename and export name changed with Next.js 16: proxy.ts exporting proxy, where 13–15 used middleware.ts exporting middleware. The body is identical.

This one fails loudly, which is a mercy. Wrong filename, wrong export name, or a matcher that misses the route, and the bound root throws. It does not quietly fall back to baseline. If you see a startup error mentioning the handler, this is it.
04

Two surfaces: optimization.request versus the top-level members

If you remember one Next.js-specific thing, this is it. The binding gives you the same components twice, and the difference is whether they read the request.

The request family derives URL, route key, page payload, headers, and cookies from the forwarded request context automatically — per visitor, one Experience API round trip per request, not shareable. The top-level members take explicit inputs only and never touch next/headers or cookies(), which is precisely what makes their output cacheable.

Four members hang off optimization.request: OptimizationRoot, OptimizationProvider, OptimizedEntry, and NextAppAutoPageTracker. Mixing a request component into a route you intended to cache is the mistake this naming convention exists to prevent.

05

The handoff

The server resolved a variant. Now the browser has to hydrate without undoing that. The handoff is the object that carries the decision across, and two of its fields do the real work.

cache.scope declares who the render belongs to — private-request for a per-visitor render, or a public permutation for one shared across visitors. hydration: 'preserve-server' is what stops the variant flashing back to baseline when React takes over.

The request family builds its handoff for you and marks it private-request. You only construct one by hand when you are deliberately building something shareable.

06

Root, tracker, entry — the three things you render

OptimizationRoot wraps the participating tree: provider plus initial page-event wiring. (OptimizationProvider is the same thing without the page-event wiring.) NextAppAutoPageTracker emits the page view. OptimizedEntry is a render prop that hands your component the resolved entry.

Three constraints, each of which will catch you once. The tracker reads search params, so it must sit inside a Suspense boundary. Exactly one owner emits the initial page event — server or browser, never both, or every visit double-counts. And OptimizedEntry accepts exactly one source: baselineEntry if your app fetched it, or entryId / managedEntry if you configured contentful: { client } and want the SDK to fetch. Passing two is an error, not a preference.
07

A personalized route is a dynamic route

Primitive 06 in part one, expressed as Next.js config. Reading cookies or headers opts a route out of static generation — which is correct and what you want. The failure mode is leaving static-generation directives on that same route, where the two intentions contradict each other.

A route that genuinely must stay cached has two honest options: keep personalization client-side there and accept the flash, or serve it from a public-permutation handoff. What it cannot do is run the per-request server preflight for its own markup.
