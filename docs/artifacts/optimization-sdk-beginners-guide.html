The idea in one paragraph

One entry, many visitors, one variant each

An author attaches experiences — A/B tests or audience-targeted variants — to a content entry inside Contentful. Your app fetches that entry and its attached experiences the way it fetches anything else, then hands each entry to the SDK. The SDK reads the current visitor’s profile, picks the matching variant, and renders it — falling back to the original (“baseline”) entry whenever nothing matches. Your whole job is to wire things so that choice can happen on the server, before the HTML is sent, so the visitor never sees the baseline flash and then swap.

The map

Four wires, plus one fetch rule

Personalization in this repo is four connected pieces and one thing you must get right about the fetch. Everything after this section walks them in order. Here is the whole map on one screen:

Trust the package, not the tutorials

The general personalization docs describe a pre-1.0 API — createNextjsAppRouterOptimization, a bare /app-router import, an initialPageEvent prop. None of those exist in v1.x, and following them fails at build with Can’t resolve '@contentful/optimization-nextjs/app-router'. The authoritative reference for the installed version is node_modules/@contentful/optimization-nextjs/README.md. This guide follows the real v1.2.0 surface.

Step 1

Forward the request

src/proxy.js

Variant selection depends on who is asking, but Server Components can’t see the raw request by default. A proxy forwards a sanitized copy of it — the URL, cookies, and headers the SDK needs.

  • This boundary is required, not optional. The request-personalized runtime depends on it for the forwarded URL. Skip it and selection can’t run at all.
  • The filename tracks the framework version. Next.js 16 uses proxy.js with a proxy export; 13–15 used middleware. Same body, different name.
  • The matcher must cover your personalized routes and exclude api, or your preview and webhook endpoints get intercepted.
Step 2

Bind the SDK once

src/lib/optimization.js

Configure the SDK a single time in a server-only module, then export the components it hands back. The optimization.request family is the surface for private, per-visitor personalization.

  • Bind exactly once. A second binding starts a second SDK instance that competes with the first.
  • optimization.request is the surface you want. It auto-derives the URL, route key, page event, headers, and cookies from the proxy’s forwarded context — you never assemble a handoff by hand. (The top-level exports are for cacheable / public and analytics-only cases; ignore them while learning.)
  • locale is a single concrete value and should match whatever your Live Preview provider uses.
Step 3

Mount the Root behind a request-time boundary

PersonalizationBoundary.jsx

This is the most Next.js-16-specific step, and where beginners hit cryptic prerender errors. Two rules make it work.

Rule A — everything browser-side goes inside <OptimizationRoot>. The hooks need its context, and the preview panel binds to the window.contentfulOptimization singleton it creates.

Rule B — the Root lives behind await connection() inside a <Suspense>. The SDK stamps its event payload with new Date(), an unstable value Next.js refuses to prerender. await connection() opts the subtree into request-time rendering, which personalization needs anyway. A <Suspense> boundary alone does not do this — Suspense controls streaming, not whether a value may be prerendered.

The gotcha this repo learned the hard way

page.jsx needs its own <Suspense> and await connection(), even though the layout already has one. Next.js prerenders a layout and its page-children as separate units, so the layout’s boundary is not an ancestor for prerender analysis. Miss it and you get: connection() accessed outside of <Suspense>. Note too that personalization is scoped to /[slug], not the root layout — so routes that don’t personalize never wait on the preflight.

Step 4

Fetch deep, or it fails silently

src/lib/client.js

When an author attaches an experience, the entry grows nested reference fields: nt_experiences → nt_variants → the variant entry → that variant’s own assets. That nesting is deep, and it drives the single most common beginner failure.

If “personalization isn’t working,” check this first

Under-fetch the depth and variants resolve to baseline with no error — the page just looks un-personalized. 10 matches what the SDK’s own managed fetch uses. Links left unresolved past the include depth become baseline silently, with nothing to point at.

In this repo the app owns its own fetch (Delivery API, cached with Next 16 "use cache") and hands entries to the SDK as baselineEntry. The SDK can fetch for you instead — configure contentful: { client } and pass entryId — but owning the fetch avoids duplicating it and its cache.

Step 5

Wrap each entry so it can become a variant

ComponentResolver.jsx

The swap happens here. Wrap every content entry in <OptimizedEntry>, give it the baseline, and render from the resolved result.

  • The variant is resolved before markup is built, so no baseline content flashes and then swaps.
  • No match → baseline. That’s normal, not an error. Every visitor always sees something.
  • Wrapping at the resolver (not inside each leaf) keeps Hero, Duplex, and the rest as plain props-in / JSX-out functions. Anything you add to ComponentMap becomes personalizable automatically.

Why there are two resolvers

Published and draft render differently. ComponentResolver is a Server Component for the published path and ships zero Live Preview JS. LivePreviewResolver is a Client Component for the draft path; it imports OptimizedEntry from …/client (the only variant that accepts per-entry liveUpdates) so an author previewing edits sees variant resolution and live edits compose. page.jsx picks between them from draftMode(). Add a component once to ComponentMap and both paths get it.

Refinements

What you can defer until a variant renders

Once the five pieces above put a variant on screen, these refine it. All are configured in src/lib/optimization.js or mounted inside the boundary — none are needed to see personalization work.

  • Consent. Gates whether the SDK may emit events or persist a profile. This repo derives it from OneTrust’s cookie; the browser starts fail-closed and a sync component corrects it on mount.
  • Analytics events. allowedEventTypes plus NextAppAutoPageTracker control tracking; the page event feeds experiment reporting.
  • Interaction tracking. trackEntryInteraction (views / clicks / hovers) powers component and experiment reporting. Insights is built in — there is no separate plugin.
  • The preview panel. Shown only in Draft Mode, it lets authors force audiences and experiences to test each variant.

Minimum viable wiring

Get it working end to end

  1. Env vars. NEXT_PUBLIC_OPTIMIZATION_CLIENT_ID, NEXT_PUBLIC_OPTIMIZATION_ENVIRONMENT, plus your Contentful space / env / delivery keys.
  2. Proxy. Export proxy from createNextjsOptimizationContextHandler(); matcher covers personalized routes and excludes api.
  3. Bind once. bindNextjsAppRouterServerOptimization(…); export OptimizationRoot, OptimizedEntry, NextAppAutoPageTracker from optimization.request.
  4. Boundary. Mount <OptimizationRoot> behind await connection() inside <Suspense>, scoped to the personalized route — and repeat the connection() + Suspense in page.jsx.
  5. Fetch deep. include: 10 so the experience nesting resolves.
  6. Wrap entries. <OptimizedEntry baselineEntry={entry}>{(resolved) => …}</OptimizedEntry>.

If variants aren’t showing, check in this order

  1. Fetch depth — the silent one, and the most common. Is include deep enough?
  2. Proxy matcher — does it actually cover this route?
  3. The entry — does it really have an experience attached in Contentful?
  4. Consent — is it blocking selection or events?
  5. await connection() — present in both the boundary and page.jsx?
