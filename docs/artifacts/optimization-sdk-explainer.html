The one idea

Everything is one request and one join

If you take away nothing else, take this. The SDK asks a Contentful service who this visitor is, and gets back a small decision object:

Then it performs a join. You fetch a normal Contentful entry — the baseline — and the SDK combines it with selectedOptimizations to hand back either the authored variant entry or the baseline, unchanged.

That is the whole product surface. Everything else in the suite exists to answer two questions: where does that join happen, and who owns the visitor's identity while it happens.

Read path

Experience API

Evaluates audience rules and experiment splits, returns the profile and the variant selections. Called by page(), identify(), track(), screen().

Write path

Insights API

Receives behavioural events — entry views, clicks, hovers, custom events — that build profiles and score experiments. Without it, you personalize but cannot measure.

Fallback is a feature, not a failure

If consent is denied, no audience matches, links are unresolved, or the payload is all-locale, the join returns the baseline. That is a valid render, not an error state. Note the corollary: a control assignment also returns the baseline entry but still carries a defined selection at variantIndex: 0 — so never infer "nothing matched" from "I got the baseline back."

The boundary

Two runtimes, one visitor

Underneath every package sits a single shared core, and it ships in exactly two modes. This split is the most useful thing to understand, because nearly every real integration question resolves to "which side of this line am I on?"

Server side

CoreStateless

Holds no state between requests. Every method returns per-request values. It stores no cookies, no profile, nothing — persistence is the application's job. You create one instance for the process and derive a fresh, request-scoped client per incoming request.

@contentful/optimization-node Also backs the server half of the Next.js adapter.
Client side

CoreStateful

Long-lived and reactive. Owns state as observable signals, a consent gate, an event queue, the anonymous-ID cookie, browser storage, and DOM observation for interaction tracking. Enforced as a singleton — a second instance throws.

@contentful/optimization-web @contentful/optimization-react-web

Primitives

What you actually hold in your hands

The client side is declarative — you compose components and read hooks. The server side is imperative — you bind a request and call methods. Same concepts, different ergonomics.

Client · React

Components & hooks

<OptimizationRoot>
The single entry point. Mount it once around everything that uses the SDK. It is a convenience wrapper that composes three providers for you — OptimizationProvider, LiveUpdatesProvider, and InteractionTrackingProvider — so you configure by props instead of wiring providers by hand.
<OptimizedEntry>
The workhorse. Takes a baseline entry, performs the join, and gives you the resolved entry through a render prop. Also emits the metadata that makes view/click/hover tracking automatic. Accepts either baselineEntry (you fetch) or entryId (the SDK fetches) — never both.
useOptimizationActions()
The verbs: setConsent, identifyUser, trackEvent, trackPageView, trackScreen, resetUser, flushEvents.
useConsentState() · useProfileState() · useSelectedOptimizationsState()
The nouns. Read-only reactive views of the current state, for building your own consent UI or debug panel.
AutoPageTracker
Router-specific. One per router tree; dedupes consecutive routes for you. Adapters ship for React Router, TanStack Router, and both Next routers.
attachOptimizationPreviewPanel()
Optional in-browser panel for authors to impersonate audiences. Separate package; gate it out of production builds.
Server · Node

Singleton & request client

new ContentfulOptimization()
Created once at module level — never inside a request handler. It holds no visitor state, so reuse is safe and per-request construction is the classic mistake.
optimization.forRequest({ … })
The heart of the server model. Binds consent, the incoming profile ID, locale, and page context to this request and returns a scoped client. Consent is a required argument — there is no singleton consent() method on the server.
requestClient.page() / .identify() / .track()
Live on the request client, not the singleton. Each returns a discriminated { accepted, data? } — check accepted before reading data. A blocked event returns false; it does not throw.
fetchOptimizedEntry() · resolveOptimizedEntry()
Managed (SDK fetches and joins) versus manual (you fetch, then pass the baseline and selections in explicitly).
ANONYMOUS_ID_COOKIE · canPersistProfile
Because the server stores nothing, you read the cookie into forRequest and write it back — but only when canPersistProfile is true.
trackView() · trackClick() · trackFlagView()
Server-side Insights, available but manual. Most teams let the browser own measurement.

One rule prevents most confusing errors

Respect the import boundary. Server Components import from the Node package only; Client Components import from the React Web package only. Crossing that line produces runtime failures that trace back to the stateful/stateless split and are genuinely hard to diagnose from the symptom.

The loop

Order of operations

This sequence is genuinely ordered — get it out of order and you render the baseline forever, which is the single most common "personalization isn't working" report. Numbers here mean real steps.

  1. Initialize oncebothOne root in the browser, one singleton in the process. Duplicates are the second most common failure.
  2. Establish consent and identitybothSeed consent and any known profile ID before emitting events. Two independent axes: may we send events, and may we persist a profile.
  3. Identify a known userbothOnly if you have one. Links your application's user to the anonymous profile.
  4. Emit the initial page eventone ownerThis is the call that returns selections. In a hybrid app exactly one runtime may own it — if the server emitted it, the browser tracker must be told to skip, or you double-count.
  5. Resolve entriesbothNow, and only now, does the join have anything to work with. Resolving before an accepted event returns the baseline.
  6. Track interactionsbrowserViews, clicks, hovers flow to the Insights API using the resolved entry ID. This is what makes experiment reporting work.

Where to resolve

Flash versus cacheability

This is the real architectural decision, and it is a genuine trade-off rather than a best practice. Resolving in the browser keeps your HTML static and shareable but shows the baseline first. Resolving on the server removes that flash but makes the route render per visitor.

Choosing a resolution point
ApproachFirst paintRoute cacheabilityReach for it when
Client-only Baseline, then swaps Fully static / CDN The framework is client-only (Vite, CRA, Gatsby), the personalized surface is below the fold, or the route's shared cacheability is non-negotiable.
Server (hybrid SSR) Variant, no flash Dynamic per request The default for Next.js and other SSR frameworks. Hero and above-the-fold personalization, where a flash undermines the whole point.
Edge + permutation cache Variant, no flash Shared per permutation High-traffic pages that need both. Costs you a modelling exercise: the variant space must collapse into a manageable set of permutations.
Server-only Variant, no flash Dynamic per request Rarely. No browser runtime means no interaction tracking, so experiment reporting suffers. Choose it only when client JS is genuinely unavailable.

How to frame this in a room

Don't lead with "SSR is better." Lead with the question: is the personalized content above the fold? If yes, resolve on the server and accept a dynamic route. If no, resolve in the browser and keep the CDN. Teams that skip that question tend to convert a happily-cached site into a dynamically-rendered one to remove a flash nobody would have seen.

The constraint people trip over

A route that resolves personalization server-side reads cookies and headers, so it renders per request. It cannot also be statically generated or ISR-cached. If you leave generateStaticParams, force-static, or a revalidate directive on a personalized route, you have written two contradictory intents — and the build summary may still print the static marker even though nothing is prerendered.

Adapter vs. manual

Two ways to build the same hybrid app

For an App Router application you have a real choice: compose the Node SDK and the React Web SDK yourself, or install the Next.js adapter that binds them for you. Both produce a hybrid app. The difference is entirely about who owns the handoff.

The part worth flagging early

That proxy.js / middleware.js file is not optional when server personalization is enabled. It forwards the request context that the bound components depend on. If it is missing or misnamed for your Next.js major version, the bound root throws — it does not quietly fall back to the baseline. It is the first thing to check when a new integration won't start.

Expect some naming drift in the docs

The adapter's public surface has moved during the 1.x line. As of 1.2.0 the App Router entry points are bindNextjsAppRouterServerOptimization from /app-router/server and its client counterpart under /app-router/client. Some published guides and AI-assistant references still show an earlier createNextjsAppRouterOptimization from a bare /app-router subpath, which this version does not export. Trust the installed package's exports and README over any prose, and pin your suite versions together.

Gotchas

The short list that saves a week

Almost every "it renders the baseline and I don't know why" ticket is one of these. None are obvious from the symptom.

Content & data

Fetching

  • One concrete locale. Never locale=* or withAllLocales — locale-keyed field maps cannot be resolved and silently fall back to baseline.
  • Enough link depth. The chain is entry → nt_experiences → nt_variants → variant content. Shallow includes leave unresolved links, which are filtered out, so nothing personalizes. The managed path uses include: 10; match it manually.
  • Publish in dependency order. Variants, then experiences, then the baseline. The Delivery API only sees published content, so personalization can work in preview and fail in production.
Runtime & state

Wiring

  • ctfl-opt-aid must not be HttpOnly. The browser SDK reads it from document.cookie at startup. Mark it HttpOnly and server/client profile continuity breaks — quietly.
  • One owner for the initial page event. Otherwise you double-count every visit.
  • Deduplicate page() across Server Components. Wrap it in React's cache() or every component triggers its own Experience API call for the same request.
  • Blocked events are silent. They return { accepted: false } rather than throwing. Use onEventBlocked or the blocked-event stream when tracking seems to vanish.
  • Live updates are opt-in. Entries lock after first resolution. If content should change after login or a consent grant, enable it — but don't enable it to fix a broken first render.

Consent, briefly

Two independent axes: may we send events, and may we persist a profile. Tracking is gated by default; only identify and page are admitted pre-consent in the web runtimes. The SDK renders no consent UI and does not own your consent record — you call it from whatever banner or CMP you already have. Absent any decision the state is undefined, not false; tighten that to fail-closed with an empty allowed-events list if your policy demands it.

The suite is the recommended path for all new Personalization and Analytics work, and it fully replaces the legacy Ninetailed experience.js SDKs. Existing production integrations on experience.js remain supported with no announced deprecation date, and there is no automated migration tool — the provider lifecycle, consent model, identity handling and rendering contracts all differ, so treat a migration as a deliberate project rather than an import rename.
