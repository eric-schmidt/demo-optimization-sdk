Cache-Safe Personalization

Everything in this guide follows from one fact: HTML personalized for one visitor cannot be shared with another. Cache Components give you sharper tools for deciding what gets cached — and sharper ways to get it wrong. Grounded in demo-optimization-sdk: its three ADRs, its measurements, its stress harness.

Model

What changed from unstable_cache

You already know the shape of the old model: wrap a non-fetch data source in unstable_cache, hand it explicit keyParts, declare tags up front, and invalidate with revalidateTag. Cache Components keep the destination and change the mechanics. One directive — "use cache" — caches the return value of any async function, and cacheTag / cacheLife are called inside it.

That inversion is the whole story. Because the tag calls now run after the data arrives, tags can reference the response rather than the arguments.

The three limitations that forced the migration — ADR 0001
Under unstable_cache Under Cache Components
The Contentful JS SDK uses Axios, not fetch, so the next: { revalidate, tags } options were unreachable. unstable_cache was the escape hatch, and it needed manual keyParts. "use cache" wraps any async function. The Axios/fetch mismatch disappears; no adapter workarounds, no hand-written key parts.
Tags were declared before the fetch, so they had to derive from arguments — in practice, the slug. Renaming a slug in Contentful stranded the cache entry behind a tag no webhook payload could ever match. Tag by sys.id instead. Tag identity is stable across renames, because sys.id never changes.
Invalidating a nested entry meant the webhook handler had to rebuild the reference graph at revalidation time — a recursive walk up the tree, gated by a hard-coded content-type allowlist. Tag every entry and asset in response.includes at fetch time. Any referenced-entry publish invalidates the parent page directly.

The payoff is visible in the webhook handler, which collapsed from roughly fifty lines — getEntryById, getLinksToEntryById, findPageToRevalidate, a pageContentTypes allowlist — to one call: 

// src/app/api/revalidate/route.js — the whole invalidation strategy
revalidateTag(payload.sys.id)

A cacheHandler override also disappeared. It existed only to dodge the 2 MB value ceiling in unstable_cache; that rationale left with the primitive.

What the fetch layer looks like now

// src/lib/client.js (condensed)
const getPublishedEntriesBySlug = async ({ contentType, slug, includeDepth = 10 }) => {
  "use cache";
  cacheLife("contentful");            // stale 300 · revalidate 900 · expire 3600
  cacheTag(`${contentType}:${slug}`);  // so an empty result can still be invalidated

  const response = await client.getEntries({ content_type: contentType, include: includeDepth, ... });

  // every Entry/Asset in the tree — including unresolved link stubs one level
  // deeper than `include` resolved — becomes an invalidation tag
  for (const id of collectContentfulIds(response)) cacheTag(id);

  return items;
};

One nuance worth internalizing: the public getEntriesBySlug is a plain dispatcher that calls this only when preview is false. Draft reads bypass the cache entirely — the Preview API must never be cached — and keeping that branch outside the cached function is what lets "use cache" stay static.

Primitives

The five things you actually touch

Cache Components surface used in this app
Primitive Where it goes What it does
cacheComponents: true next.config.js Turns the model on. Without it, none of the rest applies.
"use cache" First line of an async function or component Caches the return value, keyed on the arguments.
cacheLife(profile) Inside the cached function Picks a named freshness profile. This app defines "contentful" in next.config.js.
cacheTag(...) Inside the cached function, after the data arrives Attaches invalidation handles. This is the call that can now see the response.
await connection() next/server, top of a request-time subtree Declares "this is request work, do not prerender it." The one that bites — see below.

The architectural consequence: your root layout prerenders fully, and each page becomes a static shell plus a Suspense-bounded dynamic region. A route that builds as ◐ Partial Prerender is working correctly — that symbol is not a warning.

Rule

Suspense is not a request boundary

This is the single most expensive misunderstanding available in this stack, so it is worth stating precisely. <Suspense> controls streaming. It does not control whether a value may be prerendered. Awaiting draftMode() nearby does not either. Only an explicit dynamic data access — await connection() — moves a subtree to request time.

It surfaces here because the Optimization SDK builds event payloads that stamp new Date().toISOString(). Next.js refuses to prerender an unstable value: 

Route "/[slug]": Next.js encountered the unstable value `new Date()` while prerendering.

Why this one hides

The route still returns HTTP 200 while logging that error, and the error lands in .next/dev/logs/next-development.log rather than your terminal. A broken prerender looks like a working page.

And it is per boundary, not per app. Each Suspense boundary is prerendered independently, so a connection() call in a layout does not cover a page's own boundary. In this repo that lesson is now baked into the structure: personalization was deliberately consolidated from two nested boundaries into a single private slot, so there is exactly one boundary, one connection() call, and one place to get it right. 

// src/app/[slug]/PrivateRequestSlot.jsx
export const PrivateRequestSlot = async ({ params }) => {
  await connection();  // ← everything visitor-specific lives below this line
  ...
};

If you add a new Suspense boundary that renders the optimization root or an optimized entry, it needs its own call.

Tension

Why personalization fights caching

Personalized HTML resolved per visitor cannot be shared.

Server-side resolution buys something real — the visitor's variant is in the initial HTML, so there is no flash of baseline content and no post-hydration swap. The cost is that the output is now specific to one person, and a shared cache is a machine for giving one person's output to somebody else.

The SDK makes this explicit rather than implicit. Every render produces a handoff carrying a cache scope — an SDK-owned exact value, not an app convention. Learn these three and most of the model follows.

private-request

A real request backed by cookies, headers, or an Experience API response for one visitor.

Rule: keep the output out of shared caches.

public-permutation

An app-owned segment, market, campaign, or path where application code already chose the selections.

Rule: must carry a helper-built cache.key.

static

Build-time output with no profile state in it at all.

Rule: no profile state.

The insight that makes the rest of this guide make sense: who chose the variant determines whether the HTML can be shared. If the Experience API chose it for this visitor, it is private. If your application chose it from its own registry, it is shareable — because every visitor asking for that permutation gets byte-identical output.

Paths

Two paths, one variant

This repo runs both models deliberately, on separate routes, and chooses per route. Same content, same resolved variant, radically different cost and risk.

The counter-intuitive line in proxy.js

The proxy matcher excludes the cached route. That looks like an oversight and is the opposite: withholding per-visitor request context from that route is precisely what keeps its output shareable. Do not "fix" it.

Measured on this app, production build, warm cache
private-request public-permutation
p50 96ms (158ms under load) 8ms (24ms under load)
p95 under load 282ms 26ms
Hero variant correct correct — identical
Profile state in HTML yes none
Shared across visitors no yes, byte-identical
Experience API outage renders no content unaffected

Roughly 6.5× at p50 and 10× at p95, rendering the same variant. The price is that permutations are enumerated by hand, and the cost is combinatorial in audience count — fine for a handful of segments, wrong for per-user personalization.

The models cannot be layered. Request-derived profile handoffs are private-request only, so this is a per-route either/or.

Cost

Where the time actually goes

Worth knowing because the instinct is to blame payload size, and the instinct is wrong. Server-side segments inside the private slot, warm:

Private-slot segment timing
SegmentTime
await connection()0.6–1.3ms
params + draftMode()~0ms
getEntriesBySlug (cached)0.3–0.7ms
Total in-component work1.0–2.0ms
Actual response~96ms

Point the SDK at an unreachable Experience API and the response collapses to ~11ms. Cold TLS to experience.ninetailed.co alone measures 56–80ms from a developer machine. Essentially all per-request latency is one live Experience API round trip, awaited during the optimized-entry render. On this path it is irreducible — that call is how the visitor's profile and selected optimizations are obtained.

Three plausible wrong turns, already taken

Each was tested and discarded. Recorded so nobody re-litigates them:

  • The include: 10 payload is expensive to deserialize. False — timing is flat within noise from depth 10 down to 2, and response bytes are identical.
  • The request handler is misconfigured, breaking profile continuity. False — the no-argument forwarding handler is the documented default; the request family evaluates the request itself.
  • The Contentful fetch is the cost. False — it measures 0.3–0.7ms through the existing "use cache" layer.

Structure

Why there are three resolvers

A detail that looks like duplication and is actually the architecture. The component that wraps an entry differs by cache ownership, and cache ownership cannot be decided at runtime — "use client" is a bundler input, not a runtime switch. So the fork is structural.

One entry boundary, three cache owners
Resolver Runs Path SDK surface
ComponentResolver Server Published RequestOptimizedEntry
LivePreviewResolver Client Draft unbound /client entry — the only one taking per-entry liveUpdates
PermutationResolver Server, cached Permutation ExplicitOptimizedEntry

The reason it is worth the duplication: the published path ships zero Live Preview JavaScript. Before the split, every cached page render shipped a live-updates subscription that only ever mattered in draft mode.

The maintenance tax

Anything applied at the entry boundary must be applied in all three. The live example is empty-variant suppression: when an author chooses to show nothing to an audience, the SDK still hands back the baseline entry so tracking has context. Render it unconditionally and you show the baseline exactly where the author chose silence. Every resolver has to check resolvedData.isEmptyVariant for itself.

Guardrails

What the SDK catches for you

Genuine good news, and the honest framing for a customer conversation: cache-safety mistakes inside the SDK's reach are loud. It throws rather than degrading quietly.

Loud failures — the SDK throws or warns
MistakeResult
Profile state in a public or static handoff TypeError: Profile state should not be included in public or static optimization caches.
Public permutation without a cache key Warning — missing-public-permutation-cache-key
Public/static cache metadata passed to a request handoff helper TypeError
Missing or misnamed request handler The bound root throws. Note it does not fall back to baseline.

Two functions make this testable rather than aspirational: getOptimizationCacheSafetyWarnings() and assertOptimizationCacheSafety(). Both are exercised directly by npm run stress, which is 14 checks covering every number and symptom in this guide.

Guardrails

What nothing catches

The more important table. Every row here returns HTTP 200 and looks like a working page. If you internalize one section of this guide, make it this one.

Silent failures — no error, no warning
MistakeSymptom
Framework or CDN caching over a personalized route — full-route cache, s-maxage, generateStaticParams One visitor's variant, flags, merge tags, and profile served to another. Demonstrated in the stress harness: a URL-keyed cache in front of /[slug] hands visitor A's profile id to visitor B. The application is correct; the cache in front of it is not.
Include depth too shallow The variant silently vanishes. At depth 2 here: HTTP 200, images intact, variantIndex quietly collapses to 0.
Missing connection() under Cache Components Prerender error logged to a file while the route still serves 200.
All-locale payload — withAllLocales, locale=* Locale-keyed field maps do not match the resolver schema. Silent baseline fallback.
Unpublished experience or variant Silent baseline. Publish order matters: variants → experiences → baseline entry.
Empty variant not suppressed The baseline renders where the author chose to render nothing.
Experience API outage The personalized region renders empty. See below.

The one that matters most

That first row is the row to raise in every architecture review. Correct application code plus one well-meant CDN rule equals cross-visitor profile leakage — and nothing in the stack will tell you. Personalized routes must be excluded from shared caching by explicit decision, written down, owned by someone.

Failure

A personalization outage is a content outage

Measured, not theorized. With the Experience API returning 503, the private-request path serves HTTP 200 and an 11.5 KB shell: no <h1>, no images, zero data-ctfl attributes. The SDK throws on an unretryable failure, the error escapes the private slot, and the visitor gets a blank region.

This is not a graceful fallback to baseline. Anyone adopting SSR personalization should hear that sentence plainly, early, from you rather than from an incident. Two mitigations, both real:

  • An error boundary around the personalized region that renders baseline content.
  • Move the route to the permutation path, which is unaffected because the Experience API is not on its render path at all.

Detail

Two counter-intuitive details

Include depth is topology-dependent

The link chain here implies a floor of 5 (landingPage → hero → nt_experience → variant → mediaWrapper → asset), but the empirical floor is 3 — Contentful resolves links from a flat includes pool, so the variant reuses assets already pooled via the baseline path.

A variant with its own deeper content would break at 3 with no error. That is why include: 10 is kept even though it measures no cost: the headroom is the point.

handoff.cache.key is not a cache key

Despite the name, it is not a Next.js cache key and not a cacheTag/revalidateTag tag. It is deterministic SDK identity and transport metadata.

Consequence with teeth: Custom Flag changes are carried in handoff state but are not fingerprinted into it. A flag whose value affects markup must be represented through the app-owned cacheVersion instead, or you will serve stale markup with a fresh flag.

Practice

Saying it to a customer

Lines that are both true and useful, in roughly the order a conversation tends to need them.

"Server-side personalization removes the flash of wrong content. It costs you a shared cache."

The whole tradeoff in two sentences. Everything technical follows from it, and it reframes the conversation from "is this fast" to "who is this HTML for."

"Decide it per route, not per project."

Above-the-fold hero: resolve per visitor, accept the round trip. Below-the-fold or non-critical: client-side is fine, the flash costs nothing. Known segments rather than individuals: permutations, and get an order of magnitude back.

"If your application picks the variant, the page is still cacheable."

The unlock most people miss. Personalization does not have to mean uncacheable — it means uncacheable when a per-visitor API call chose the variant.

"The dangerous failure is a CDN rule, not code."

Names the real risk and puts it where it belongs: infrastructure review, not the developers. It also earns trust, because it is not the answer a vendor is expected to give.

"On the SSR path, treat a personalization outage as a content outage — and put an error boundary in."

Say it before go-live. It is measured behavior, it has a cheap fix, and it is far better coming from you in design than from an incident review.

Don't say: "personalization adds about 96 milliseconds."

Those numbers are from one app, one content graph, one warm cache, on a developer machine — illustrative of shape, not benchmarks. Say "essentially all of the added latency is one round trip to the personalization API, so it scales with that call, not with your content" — same insight, defensible anywhere.
